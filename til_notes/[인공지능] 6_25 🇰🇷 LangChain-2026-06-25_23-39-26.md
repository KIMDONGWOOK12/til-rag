배운 내용 : LangChain RAG 파이프라인 (Text Splitter ~ 고급 Retriever ~ LangSmith)

예비군 이쓔로 인해 앞서 나갔던 내용 정의, 사용이유, 사용방법만 정리 해두겠숨다

**Text Splitter**

정의 : Document 리스트를 받아 각 문서를 작은 Document(chunk)로 나누는 LangChain 컴포넌트의 표준 인터페이스다.

이유 : 긴 문서에서 필요한 근거만 정확히 검색하고, LLM에 넣을 문맥 크기를 일정하게 제한해 답변 품질과 비용을 안정적으로 관리하기 위해서다.

방법 : 목적에 맞는 분할기를 골라 chunk\_size, chunk\_overlap을 정한 뒤 split\_documents()로 분할한다. 분할 후에도 원본 metadata는 각 chunk에 유지된다.

분할기 종류

    RecursiveCharacterTextSplitter : 문단/줄/공백 구분자를 우선순위대로 분할 (가장 많이 씀)
    CharacterTextSplitter          : 지정한 구분자 하나로 분할
    TokenTextSplitter              : 토큰 수 기준 분할
    MarkdownHeaderTextSplitter     : 마크다운 헤더 기준
    HTMLHeaderTextSplitter         : HTML 헤더 기준

**RecursiveCharacterTextSplitter**

정의 : 구분자 리스트를 우선순위대로 시도하면서, chunk\_size를 넘는 조각만 다음 구분자로 다시 나누는 작업을 재귀적으로 반복해 자연스러운 의미 경계로 나누는 분할기다.

이유 : 문서의 의미 경계를 최대한 보존하면서 chunk 크기를 안정적으로 통제하기 위해서다.

방법 : 빈 줄(문단) → 줄바꿈 → 공백 → 글자 순으로 시도한다. 문단으로 충분하면 거기서 멈추고, 너무 크면 더 작은 단위로 내려간다. 일반 문서 RAG의 기본 선택이다.

**CharacterTextSplitter**

정의 : 하나의 구분자만 기준으로 텍스트를 나누는 가장 기본형 분할기다.

이유 : 구분자가 일관되게 등장하는 정형 텍스트(로그, FAQ 등)에서는 단일 구분자만으로 충분하고 결과 예측이 쉽기 때문이다.

방법 : separator 하나로 나눈 뒤 조각을 chunk\_size에 맞춰 묶는다. 단, 구분자가 없으면 chunk\_size를 초과하는 조각이 남을 수 있다.

**TokenTextSplitter**

정의 : 글자 수가 아니라 토큰 수를 기준으로 분할하는 분할기다.

이유 : 글자 수와 토큰 수는 비례하지 않기 때문이다. 한국어는 한 글자가 여러 토큰이 되어, 글자 기준으로 자르면 토큰 한도를 넘길 수 있다.

방법 : tiktoken으로 텍스트를 토큰으로 변환해 chunk\_size(토큰 수)에 맞춰 나눈다. 토큰 통제는 강하지만 단어/문장 경계 보존은 약하다.

**Embeddings**

정의 : 자연어를 의미를 보존한 고정 차원 숫자 벡터로 변환하는 표준 인터페이스다.

이유 : 임베딩 모델을 바꿔도 같은 방식으로 벡터를 얻고, RAG의 인덱싱과 검색을 끊김 없이 연결하기 위해서다.

방법 : embed\_documents()로 여러 문서를, embed\_query()로 단일 질의를 벡터로 바꾼다. 의미가 가까운 텍스트일수록 벡터 공간에서 가까이 놓여, 코사인 유사도로 관련도를 잰다.

**VectorStore Interface**

정의 : Chroma, FAISS 등 모든 벡터 DB 구현체가 따르는 LangChain의 표준 인터페이스다.

이유 : DB 종류와 무관하게 같은 코드로 인덱싱/검색/Retriever 변환을 해서 DB 교체 비용을 줄이기 위해서다.

방법 : from\_documents()로 인덱싱, similarity\_search()로 검색, as\_retriever()로 Retriever 변환을 한다. 인덱싱과 검색에 같은 Embeddings 객체를 써서 문서와 질의가 같은 공간에 놓인다.

**Croma (Chroma)**

정의 : 별도 서버 없이 파이썬 환경에서 쓰는 임베디드 방식의 오픈소스 벡터 DB다.

이유 : RAG 구조를 실습하거나, 서버형 VDB를 쓰기 전 작은 데이터셋으로 검색 품질을 빠르게 검증하기 위해서다.

방법 : 임베딩 벡터/문서 내용/메타데이터를 함께 저장한다. persist\_directory를 지정하면 로컬에 영구 저장하고, 생략하면 인메모리로 동작한다.

**FAISS**

정의 : Meta가 공개한 메모리 기반 고속 유사도 검색 VDB 라이브러리다.

이유 : 대량 벡터 검색을 외부 서버 호출 없이 로컬 메모리에서 빠르게 처리해 응답 속도와 처리량을 높이기 위해서다.

방법 : from\_documents()로 인덱싱한다. 메모리 기반이라 종료되면 인덱스가 사라지므로(휘발성), save\_local로 저장하고 load\_local로 다시 불러와야 한다.

**Retriever**

정의 : 질의를 입력받아 관련 Document 리스트를 반환하고, LCEL 체인에 연결할 수 있는 LangChain의 검색용 Runnable 인터페이스다.

이유 : 검색 결과를 항상 Document 리스트로 통일해 후속 단계를 안정화하고, 검색 전략이 바뀌어도 체인 수정 범위를 줄이기 위해서다.

방법 : vectorstore[.](http://vectorstore.as)as\_retriever()로 만들어, invoke("쿼리")로 직접 호출하거나 LCEL 체인에 파이프(|)로 연결한다.

**Ensemble Retriever**

정의 : 여러 Retriever의 검색 결과를 RRF 방식으로 순위 통합해 하나의 Document 리스트로 반환하는 합성 Retriever다.

이유 : 단일 검색 전략의 한계로 인한 근거 문서 누락을 줄이기 위해서다. 키워드 검색(BM25)과 의미 검색(벡터)을 함께 써서 서로의 약점을 보완한다 (Hybrid Search).

방법 : 여러 Retriever와 weights를 등록한다. 점수가 아니라 순위를 합치므로(RRF) 계산 방식이 다른 검색 결과도 안정적으로 결합된다.

**Multi-Query Retriever**

정의 : 사용자 질의를 LLM으로 여러 변형 질의로 확장하고, 각 검색 결과를 통합해 반환하는 고급 Retriever다.

이유 : 같은 의도라도 표현이 달라 검색이 빗나가는 문제를 LLM의 질의 확장으로 흡수해 검색 누락을 줄이기 위해서다 (Query Expansion).

방법 : 기본 Retriever에 LLM을 연결한다. LLM이 질의를 여러 개로 바꿔 각각 검색한 뒤, 결과를 합치고 중복을 제거한다. 단, 정확한 문자열 매칭이 중요한 경우엔 부적합하다.

**Contextual Compression**

정의 : 기본 Retriever가 가져온 Document를 질의와 관련된 내용만 남기도록 압축해 더 짧은 리스트로 반환하는 고급 Retriever다.

이유 : 검색된 chunk가 길거나 관련 없는 부분이 많을 때 프롬프트 토큰을 줄이고 답변 품질을 안정화하기 위해서다 (Reranking 계열).

방법 : 검색은 기존대로 두고 그 위에 압축기만 얹는다. 압축기 종류로 LLMChainExtractor(관련 문장만 추출), LLMChainFilter(문서 단위 제거), EmbeddingsFilter(유사도로 빠르게 제거)가 있다.

**Parent Document Retriever**

정의 : 작은 child chunk로 검색하되, 반환은 그 chunk가 속한 parent(원본) 문서로 주는 고급 Retriever다.

이유 : 작은 chunk의 정확한 의미 매칭과 큰 chunk의 풍부한 문맥을 동시에 얻기 위해서다.

방법 : child는 VectorStore에, parent는 docstore에 저장한다. 검색은 작은 child로 정확하게 하고, 반환은 그 child의 parent 문서로 해 LLM에 넓은 문맥을 준다.

**LangSmith**

정의 : LangChain 기반 LLM 앱의 실행을 추적하고, 응답 품질을 평가하며, 프롬프트를 버전 관리하는 운영·평가 플랫폼이다.

이유 : 체인이 여러 단계로 길어지면 어느 단계에서 문제가 생겼는지 찾기 어렵기 때문이다.

방법 : 환경 변수(LANGSMITH\_TRACING=true, API 키)만 설정하면 코드 수정 없이 모든 체인 실행이 자동 기록된다. 주요 기능은 Tracing, Dataset, Evaluator, Prompt Management 등이다.

**Tracing**

정의 : 체인의 실행 흐름을 단계별 Run으로 기록하고, 각 단계의 입력/출력/지연/토큰 사용량을 트리 구조로 보여주는 LangSmith의 추적 기능이다.

이유 : 최종 답변만 봐서는 어느 단계(검색/프롬프트/모델/파싱)에서 문제가 났는지 알기 어렵기 때문이다.

방법 : LANGSMITH\_TRACING=true 상태로 체인을 실행하면 자동 기록된다. 기록 단위는 Trace(실행 전체) → Run(단계) → Span(세부)이다. 일반 함수는 @traceable로 같은 트리에 포함한다.

**Dataset**

정의 : 평가에 쓰는 입력과 기대 출력 쌍(Example)을 모아 둔, LangSmith의 표준 평가 자료다.

이유 : 프롬프트/모델 변경이 답변 품질에 주는 영향을 같은 기준으로 반복 검증하고, 실패 사례를 재발 방지 자산으로 축적하기 위해서다.

방법 : create\_dataset으로 만들고 create\_examples로 입력/출력 쌍을 추가하거나, 대시보드 Run 화면에서 "Add to dataset"으로 등록한다. 수정 시 버전이 기록된다.

**Evaluator**

정의 : 모델의 실제 출력과 기대 출력을 기준에 따라 비교해 점수와 코멘트를 반환하는 평가 함수다.

이유 : 프롬프트/모델 변경의 품질 영향을 정량 점수로 바꿔, 평가 자동화와 회귀 테스트를 가능하게 하기 위해서다.

방법 : evaluate(target=체인, data=Dataset, evaluators=\[...\])로 실행한다. 종류로 LLM-as-Judge(의미 평가), 휴리스틱(규칙), 임베딩 유사도, 사람 평가가 있고 보통 여러 개를 함께 쓴다.

**Prompt Management**

정의 : 프롬프트를 코드와 분리해 LangSmith Hub에서 등록/버전 관리/공유하고, 코드에서는 이름으로 가져와 쓰게 하는 운영 기능이다.

이유 : 프롬프트를 재배포 없이 즉시 바꾸고, 버전별 사용/성능을 한곳에서 관리하기 위해서다.

방법 : push\_prompt로 등록하면 새 버전이 쌓이고, pull\_prompt("이름")으로 가져온다. prod, staging 같은 태그로 운영 단계를 구분한다.

큰 틀

Document에서 시작해 Splitter로 나누고, Embeddings와 VectorStore로 저장하고, Retriever로 검색해 생성하며, LangSmith로 전체를 추적/평가한다.

고급 Retriever들은 결국 검색 품질을 높이는 방법이다. Ensemble은 키워드와 의미를 함께, Multi-Query는 질문을 확장, Contextual Compression은 노이즈 제거, Parent Document는 정확도와 맥락을 동시에 잡는다.

LangSmith는 만든 체인을 운영 단계에서 관찰하고 개선하는 도구다. Tracing으로 흐름을 보고, Dataset과 Evaluator로 품질을 평가하고, Prompt Management로 프롬프트를 관리한다.
