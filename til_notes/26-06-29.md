## LangGraph

*   상태를 가진 LLM 애플리케이션의 워크플로와 에이전트를 그래프 구조로 설계하고 실행하는 LangChain팀의 저수준 오케스트레이션 프레임 워크
    
*   랭그래프틑 그래프 구조로 워크플로를 설계하는 에이전트(를 만드는데에 쓰는) 프레임웍이다.
    
*   비교 ) 스프링은 웹(앱을 만드는 데에) 프레임웍이다.
    
*   사용 이유 : 분기, 반복, 상태 저장, 중단 후 재개, 사람 개입이 필요한 에이전트 워크플로를 안정적으로 구현해 유지보수 비용을 줄이고 실행 안정성을 높이기 위해서
    
*   사용 방법 : pip install langgraph -> 상태 스키마 정의 -> 노드 - 엣지 등록 -> compile() 로 그래프 생성 -> invoke() 로 실행
    

파이프라인을 세팅한다 = 실행 흐름을 미리 그래프로 설계한다

## WorkFlow

*   개발자가 미리 정의한 실행 경로와 조건 분기를 따라 상태를 단계적으로 처리하는 LLM 애플리케이션 구조
    
*   (랭그래프에서의) 워크플로우는 단계적으로 상태를 처리하는 앱 구조다.
    
*   사용 이유 : 복잡한 AI 처리 흐름을 예측 가능하고 검증 가능한 구조로 고정해, 운영 중 오류·비용·품질 문제를 안정적으로 통제하기 위해서
    
*   사용 방법 : 노드와 엣지로 처리 순서를 정의한 뒤 compile() -> invoke()로 실행
    

## AI agent

*   개발자가 정의한 범위 안에서 LLM이 현재 상태를 바탕으로 다음 행동을 선택하고, 필요한 도구를 호출하며 작업을 이어가는 LLM 애플리케이션 실행 구조
    
*   에이전트는 AI를 써서 어떤 행동을 하게 한다 실행 구조다.
    
*   사용 이유 : 실행 경로를 미리 고정하기 어려운 문제에서 LLM이 상황에 맞게 도구를 선택하고 작업을 이어가도록 하기 위해서
    
*   사용 방법 : LLM 노드와 도구 실행 노드를 순환 연결하여 의사결정 루프를 구성
    

## Graph API

*   stateGraph 클래스로 노드, 엣지, 상태 스키마를 명시적으로 선언하여 그래프를 구축하는 LangGraph의 기본 프로그래밍 인터페이스
    
*   Graph API는 상태 스키마, 노드, 엣지를 가지고 그래프를 구축하는 랭그래프의 기본 API다.
    
*   사용 이유 : 복잡한 분기,반복,병렬 흐름을 코드와 시각화로 명확히 드러내, LLM 애플리케이션의 실행 경로를 안정적으로 설계,검증,디버깅하기 위해
    
*   사용 방법 : StateGraph(Schema) -> add\_node() -> add\_edge() / add\_conditional\_edges() -> compile() -> invoke()/ stream()
    

## StateGraph

*   상태 스키마를 기반으로 노드와 엣지를 등록하여 실행 가능한 그래프를 구축하는 LangGraph의 핵심 빌더 클래스
    
*   상태 스키마를 기반으로 그래프 빌더 클래스다.
    
*   사용 이유 : 여러 노드가 공유하는 상태와 실행 흐름을 구조적으로 관리해, 복잡한 LLM 워크플로를 예측 가능하고 디버깅하기 쉬운 그래프로 만들기 위해
    
*   사용 방법 : StateGraph(스키마) -> add\_node() -> add\_edge() => comile() -> invoke()
    

## Graph State Schema

*   LangGraph 그래프에서 모든 노드가 공유하는 State의 키, 타입, 병합 규칙을 선언한 상태 구조 정의
    
*   사용 이유 : 그래프 전체에서 오가는 State의 구조를 명확히 고정해, 노드가 많아져도 데이터 흐름을 예측 가능하게 관리하고 상태 관련 버그를 줄이기 위해서
    
*   사용 방법 : TypedDict로 키 이름과 타입을 선언하고, 필요하면 Annotated로 Reducer를 지정한 뒤 StateGraph(Schema)에 전달
    

## Reducer

*   특정 상태 키에 들어오는 업데이트를 기존 값과 어떻게 합칠지 정의하는 함수
    
*   1\. 함수다
    
*   2\. 합치는 로직을 담은 함수다.
    
*   3\. 기존(old) 값과 새(new)값을 합치는 로직을 담은 함수다.
    
*   여러개의 입력을 하나의 출력으로 만든다
    
### Map Reduce 패턴
    
*   N의 데이터가 들어온다.
        
*   Map -> 하나를 하나로 바꾼다.
        
*   1 -> “1” Map
        
    

### Reduce 패턴
    
*   여러개를 하나로 바꾼다
        
*   “1”, “2”, “3” -> “123”
        

*   사용 이유 : 여러 노드가 같은 State 키를 갱신해도 데이터가 덮어써지거나 충돌하지 않도록, 누적·병합 규칙을 명확히 고정해 안정적인 그래프 실행을 보장하기 위해서
    
*   사용 방법 : TypedDict의 Annotated\[Type, Reducer함수\] 타입 힌트로 키별 병합 규칙 지정
    

## MessagesState

*   Messages 키와 add\_messages Reducer가 미리 결합되어, 대화 메시지 기록을 자동으로 누적-관리 하도록 제공되는 LangGraph기본 상태 스키마
    
*   메시지를 누적하는 랭그래프 기본 상태 스키마다.
    
*   사용 이유 : 대화 기록을 매번 직접 병합하지 않아도 메시지가 안정적으로 누적·관리되게 해서, 채팅봇과 에이전트의 상태 관리를 단순화하고 구현 오류를 줄이기 위해서
    
*   사용 방법 : StateGraph(messagesState)로 그래프를 생성하면 messages 키에 병합 규칙이 자동 적용. 호출 간 기록 유지에는 checkpointer가 필요
    

## Node

*   현재 State를 입력으로 받아 실제 작업을 수행하고, 갱신한 값을 반환하는 LangGraph의 실행 단위
    
*   1\. 함수(실행 단위)다
    
*   2\. 상태를 입력 받아 갱신할 부분을 출력하는 함수다.
    
*   3\. 상태를 입력 받아 작업을 수행하고 갱신할 부분을 출력하는 함수다.
    
*   사용 이유 : 복잡한 그래프 흐름을 역할별 실행 단위로 분리해, 각 단계를 독립적으로 테스트·수정·재사용하고 장애 지점을 빠르게 추적하기 위해서
    
*   사용 방법 : 파이썬 함수를 정의하고 add\_node("이름", 함수)로 그래프에 등록
    

## Edge

*   LangGraph에서 한 노드의 실행이 끝난 뒤 다음에 실행할 노드 또는 종료 지점을 지정하는 그래프 연결
    
*   1\. 그래프 연결이다
    
*   2\. 노드 실행을 표현하는 유향(directed)그래프 연결이다.
    
*   사용 이유 : 노드 사이의 실행 순서·분기·병렬·순환을 코드와 시각화에서 명시적으로 정의하기 위해서
    
*   사용 방법 : add\_edge(src, dst)로 순차 연결, add\_conditional\_edges(src, fn, mapping)로 조건부 분기
    

## Start

*   LangGraph에서 Invoke() 실행 시 그래프가 처음 진입할 노드를 지정하는 가상 시작 지점
    
*   invoke() 실행시 그래프가 처음 진입할 노드를 지정하는 가상 시작 지점
    
*   사용 이유 : 그래프의 첫 실행 지점을 명확히 고정해, 실행 순서를 예측 가능하게 만들고 시작 지점 누락으로 인한 구조 오류를 방지하기 위해서
    
*   사용 방법 : add\_edge(START, "first\_node") 또는 set\_entry\_point("first\_node")로 진입 노드 지정
    

## End

*   LangGraph에서 그래프 실행의 종료를 나타내는 가상 종료 노드. 노드가 END로 연결되면 해당 노드 실행 후 그래프가 종료되고 최종 state가 반환됨
    
*   “마지막 작업을 수행하는 노드”가 아니라, 마지막 작업이 끝난 뒤 그래프를 멈추는 종료 기준점
    
*   사용 이유 : 그래프가 언제 정상적으로 끝나고 최종 State를 반환해야 하는지 명확히 고정해, 실행 흐름의 누락·불필요한 반복·무한 루프를 방지하기 위해서
    
*   사용 방법 : add\_edge("last\_node", END)로 종료 지정, 또는 Conditional Edge 라우팅 함수에서 END 반환
    

## Compile

*   StateGraph 빌더를 구조 검증과 런타임 설정 적용을 거쳐 실행 가능한 그래프 객체로 변환하는 메서드
    
*   지금까지 만든 그래프 구조를 검증하고, 실행 가능한 형태로 확정하는 단계
    
*   사용 이유 : 설계한 그래프를 실행 전에 검증하고 실행 옵션을 고정해, 안정적으로 실행·재개·디버깅할 수 있는 운영 가능한 그래프로 확정하기 위해서
    
*   사용 방법 builder.comile(checkpointer=..., interrupt\_before=\[...\]) 형식으로 옵셥을 설정하여 호출
    

## Graph Visualization

*   컴파일된 그래프 구조를 Mermaid 다이어그램, PNG 이미지, ASCll 형식으로 변환하여 한눈에 확인할 수 있게 하는 LangGraph의 시각화 기능
    
*   LangGraph가 변도의 클래스로 제공하는 객체가 아니라 컴파일된 그래프 객체에서 호출할 수 있는 시각화 메서드 모음
    
*   사용 이유 : 코드만으로는 파악하기 어려운 노드 연결, 조건부 분기, 순환 흐름을 한눈에 확인하여 구조 검증과 디버깅, 팀 협업을 빠르게 진행하기 위해서
    
*   사용 방법 : 컴파일된 그래프에서 get\_graph()로 그래프 객체를 얻은 뒤, draw\_mermaid(), draw\_mermaid\_png(), print\_ascii() 중 환경에 맞는 메ㅓ서드로 시각화
    

## Tool Colling

*   LLM이 사용자의 입력을 분석한 뒤, 호출해야 할 도구의 이름과 인자를 구조화된 형태로 응답에 담아 변환하는 기능
    
*   1\. 기능이다
    
*   2\. 도구의 호출을 자동화하는 기능이다
    
*   3\. 사용자 입력의 분석 결과로 도구의 호출을 판단하는 기능이다
    
*   LLM이 판단만 할 뿐 실제 도구 실행을 하는 것은 아니다.
    
*   사용 이유 : 실시간 데이터 조회, 정확한 계산, 외부 시스템 연동 등 LLM 자체의 텍스트 생성 능력만으로는 불가능한 작업을 LLM의 판단으로 수행하기 위해서
    
*   사용 방법 : @toll 데코레이터로 파이썬 함수를 도구로 정의하고, llm.bind\_tools() 로 LLM에 도구 목록을 바인딩한 뒤, invoke()로 LLM 호출하면 응답 객체의 tool\_calls 필드에 호출 요청이 담겨 반환
    

## Tool Node

*   LLM이 생성한 tool\_calls를 받아 해당 도구 함수를 실제로 실행하고, 그 결과를 Toolmessage로 변환해 메시지 리시트에 추가해 주는 LangGraph의 사전 구성(Prebuilt) 노드
    
*   1\. 노드다
    
*   2\. 사전 구성 노드다
    
*   3\. 툴 LLM이 생성한 도구 선택을 바탕으로 실제 수행하여 결과 메시지를 만드는 사전 구성 노드다.
    
*   사용 이우 : 도구 호출 요청을 받아 함수를 매칭하고, 실행하고, 결과를 메시지 형식으로 변환하는 반복적인 로직을 직접 구현하지 않고 표준화된 방식으로 처리하기 위해서
    
*   사용 방법 : ToolNode(tools=도구\_리스트)로 인스턴스를 생성하고, builder.add\_node("tools", tool\_node)로 그래프에 등록한 뒤, 조건부 엣지로 LLM 노드에서 분기
    

## Routing

*   현재 state나 입력값을 기준으로 그래프의 다음 실행 노드를 선택하는 LangGraph의 분기 설계 패턴
    
*   1.  디자인(설계) 패턴이다
    
*   2\. 입력 또는 상태에 기반하여 다음 실행 노드를 선택하는 (디자인) 패턴이다.
    
*   사용 이유 : 입력 유형과 현재 State에 따라 실행 경로를 분리해, 복잡한 분기 로직을 예측 가능하고 테스트 가능한 그래프 구조로 관리하기 위해서
    
*   사용 방법 : 라우팅 함수(상태를 받아 다음 노드 이름을 반환)를 정의하고, add\_conditional\_edges(source, route\_fn, mapping)로 소스 노드와 분기를 연결
    

## Parallelization

*   하나의 노드에서 여러 노드로 동시에 연결되어 동시에 실행되고, 모든 병렬 노드가 끝나면 다음 노드로 진행되는 LangGraph의 병렬 실행 패턴
    
*   1\. 병렬화는 (디자인) 패턴이다.
    
*   2\. 병렬화는 병렬 실행을 위한 패턴이다.
    
*   3\. 병렬화는 하나의 노드로부터 여러 노드에 연결되어 동시에 실행된 후 모든 노드의 결과를 취합하는 병렬 실행 패턴이다
    
*   사용 이유 :서로 독립적인 작업을 동시에 실행하여 전체 처리 시간을 단축하고, 외부 API 호출이 많은 워크플로우의 응답 지연을 줄이기 위해서
    
*   사용 방법 : 하나의 소스 노드에서 여러 노드로 add\_edge()로 연결하고, 병렬 노드가 같은 상태 키에 쓴다면 그 키에 Reducer를 지정한 뒤, 결과를 통합할 다음 노드(merge 등)로 다시 합류시킴

## Command

*   노드가 상태 없데이트와 다음 실행 노드 지정을 하나의 반환값으로 함께 전달할 수 있게 하는 LangGraph 객체
    
*   1\. Command는 객체다
    
*   2\. Command는 랭그래프 객체다
    
*   3\. Command는 상태 갱신과 다음 노드 지정을 할 수 있는 랭그래프 객체다

## ReAct Pattern

*   LLM이 추론하고, 필요한 도구를 실행한 뒤, 그 결과를 다시 판단에 반영하는 과정을 반복하는 LangGraph의 기본 에이전트 실행 구조
    
*   1\. 구조다.
    
*   2\. 에이전트의 실행 구조다
    
*   3\. 추론하고 실핸한 결과를 바탕으로 반복하는 에이전트의 실행 구조다.
    
*   사용 이유 : 한 번의 LLM 호출로 끝나지 않는 작업에서 도구 실행 결과를 다시 판단에 반영하며, 목표를 달성할 때까지 작업을 반복·개선하기 위해서
    
*   사용 방법 : add\_edge 또는 add\_conditional\_edges로 이미 지나온 노드를 다시 가리키는 엣지를 만들어 사용
    

## Functional API

*   일반 파이썬 함수에 @entrypoint와 @task 데코레이터를 붙여 함수 호출 흐름을 LangGraph 워크플로로 실행하는 프로그래밍 인터페이스
    
*   함수 호출 흐름을 워크플로로 실행하는 API다
    
*   사용 이유 : 기존 Python 함수 흐름을 유지하면서 LangGraph의 실행 안정성, 재개 가능성, 메모리, 스트리밍 기능을 낮은 전환 비용으로 적용하기 위해서
    
*   사용 방법 : @task로 작업 단위 함수를 정의하고, @entrypoint로 진입점 함수를 정의해 일반 Python 함수처럼 호출
    

## Persistence

*   LangGraph 그래프의 State를 실행 이후에도 유지하고, 같은 실행 흐름에서 다시 이어 사용할 수 있게 하는 상태 유지 기능
    
*   이전 state를 기준으로 이어서 동작할 수 있는 Stateful 한 실행 구조로 만들어 주는 기능
    
*   사용 이유 : 그래프 실행 상태를 저장하고 이어 갈 수 있게 해, 대화 연속성·장애 복구·중단 후 재개·디버깅을 안정적으로 지원하기 위해서
    
*   사용 방법 : compile(checkpointer=...)로 체크포인터를 연결하고 호출 시 thread\_id로 세션을 식별
