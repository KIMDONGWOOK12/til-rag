**LangChain으로 RAG 직접 구축 (개발 문서 Q&A 챗봇)**

목표

*   개인 프로젝트로 개발 기술 문서 기반 RAG 챗봇을 만들기.
    
*   직접 만든 미니GPT(생성 모델)와 달리, RAG는 외부 문서를 검색해 그 근거로 답하는 시스템.
    
*   기본 모델은 제미나이(프론티어)를 사용한다.
    

**RAG 6단계 파이프라인**

직접 짠 RAG의 각 단계가 LangChain에서는 표준 컴포넌트로 대응된다.

    단계          내가 하는 일                  LangChain 컴포넌트
    1. 문서 준비   검색할 문서 정하기             (위키 문서)
    2.  로딩        문서 읽기                  Document Loader (WebBaseLoader)
    3.  분할        chunk로 자르기             Text Splitter (RecursiveCharacterTextSplitter)
    4.  저장        벡터화 후 저장              Embeddings + VectorStore (Croma)
    5,  검색        관련 chunk 찾기            Retriever
    6.  생성        답변 만들기                 Prompt + LLM + LCEL 체인

이 6단계를 LCEL(파이프 연산자 |)로 연결하면 rag.invoke("질문") 한 줄로 동작한다.

**1\. 문서 준비, 2. 로딩**

*   정의 : Document Loader는 파일/웹페이지를 읽어 Document 객체로 변환하는 컴포넌트다.
    
*   방법 : WebBaseLoader에 URL 리스트를 주면 각 페이지를 긁어 Document로 만든다.
    

    위키백과 페이지를 URL로 로딩
    -> 불러온 문서 수, page_content 길이, metadata(source) 확인

**3\. 분할**

*   정의 : Text Splitter는 긴 Document를 검색하기 좋은 작은 chunk로 나누는 컴포넌트
    
*   이유 : 문서가 크면 검색 정밀도가 떨어지고 토큰 비용이 늘기 때문
    
*   방법 : RecursiveCharacterTextSplitter에 chunk\_size=500, chunk\_overlap=50을 주고 split\_documents()로 분할한다. 원본 metadata는 유지
    

    위키 문서 1개 -> chunk 여러 개로 분할

**4\. 저장 (임베딩 + Croma)**

*   정의 : Embeddings는 텍스트를 벡터로 바꾸고, Croma는 그 벡터를 저장/검색하는 임베디드 벡터 DB
    
*   이유 : 의미가 가까운 문서를 벡터 거리로 검색하기 위해서
    
*   방법 : GoogleGenerativeAIEmbeddings로 chunk를 벡터화하고 Chroma.from\_documents로 저장한다. persist\_directory를 지정하면 로컬에 파일로 저장돼, 다음엔 다시 인덱싱하지 않아도 된다.
    

**5\. 검색**

*   정의 : Retriever는 질의를 받아 관련 Document 리스트를 반환하는 검색용 인터페이스
    
*   방법 : [vectorstore.as](http://vectorstore.as)\_retriever(search\_kwargs={"k": 3})로 만들고 invoke("질문")으로 관련 chunk 3개를 가져온다.
    

    "인공지능이 뭐야?" -> 인공지능 관련 chunk 검색됨

**6\. 생성 (RAG 완성)**

*   정의 : 검색된 문서를 프롬프트에 넣어 LLM이 그 근거로 답하게 하는 단계다.
    
*   방법 : ChatPromptTemplate에 검색 결과(context)와 질문(question)을 넣고, 제미나이가 답하게 한다. 전체를 LCEL로 연결한다.
    

    체인 흐름:
    질문 -> Retriever 검색 -> format_docs로 문자열화 -> 프롬프트(context+question)
    -> 제미나이 답변 생성 -> StrOutputParser로 문자열 정리
    
    "인공지능이 뭐야?" -> 위키 근거로 정리된 답변 생성 성공

**트러블슈팅**

1.  웹 노이즈가 검색됨 증상 : "What is a text splitter?" 질문에 실제 설명이 아니라 페이지 공통 광고 문구가 검색됨
    
    1.  원인 : 웹페이지를 긁을 때 메뉴/광고/푸터 같은 껍데기가 chunk에 섞임 ("Skip to main content", "Navigation" 등)
        
    2.  해결 : 본문이 깔끔한 위키백과 문서로 교체 교훈 : 데이터 품질이 검색 품질을 결정한다 (Garbage In, Garbage Out)
        
2.  API 할당량 초과 (429 RESOURCE\_EXHAUSTED) 증상 : 임베딩 중 429 에러, "분당 100개 한도 초과"
    
    1.  원인 : 위키 문서 3개가 chunk 270개로 쪼개져 무료 임베딩 한도를 넘음
        
    2.  해결 : 문서를 1개로 줄이고 split\_docs\[:80\]로 chunk 수를 한도 안으로 제한 교훈 : 무료 티어는 분당/일일 제한이 있어, 대량 임베딩 시 호출량 관리가 필요하다
        

**배운 점**

RAG는 결국 "문서 -> 분할 -> 저장 -> 검색 -> 생성"의 흐름이고, LangChain은 각 단계를 표준 컴포넌트로 제공해 조립/교체를 쉽게 한다.

미니GPT(직접 만든 모델)는 학습한 것을 흉내내 답하지만, RAG는 외부 문서를 근거로 답해 환각이 적고 정확하다. 문서에 없는 질문에는 "자료에서 찾을 수 없습니다"라고 답하게 만들 수 있다.

직접 겪은 두 트러블슈팅(웹 노이즈, 할당량)은 실무에서 자주 만나는 문제이며, 데이터 품질과 비용/할당량 관리의 중요성을 체감했음다.
