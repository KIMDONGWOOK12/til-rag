**RAG 기본 파이프라인**

*   RAG (Retrieval-Augmented Generation)
    
    *   외부 문서를 검색해 LLM 입력에 넣고, 그 근거로 답변을 생성하는 구조다. (오픈북 시험) 최신 정보/내부 문서를 재학습 없이 보완하고 환각을 줄이기 위해 사용한다.
        

*   전체 흐름
    
    *   인덱싱 : 문서 로딩 -> 전처리 -> 청킹 -> 임베딩 -> 벡터 DB 저장
        
    *   질의 : 질문 -> 검색(Retrieval) -> 생성(Generation)
        

*   청킹 (Chunking)
    
    *   긴 문서를 작은 조각으로 나누는 과정이다. 고정 길이 / 구분자 기반 / 의미 기반 / 부모-자식, 4가지 방식이 있다.
        

*   토큰화 -> 밀집 벡터
    
    *   서브워드 방식으로 텍스트를 정수 ID로 바꾼 뒤, Sentence Transformers로 의미를 담은 밀집 벡터(Dense Vector)로 변환한다.
        

*   Vector DB (HNSW / ChromaDB)
    
    *   벡터를 계층 그래프로 만들어 전수 비교 없이 빠르게(정확도 99%+) 유사 벡터를 찾는 게 HNSW, ChromaDB는 학습/프로토타입용 경량 벡터 DB다. (유사도는 코사인 유사도로 측정, 1에 가까울수록 유사)
        

*   검색 -> 생성
    
    *   질문을 벡터화해 유사 청크 Top-K를 찾고, "참고하여"가 아니라 "문서만을 근거로" 답하게 해서 환각을 줄인다.
        

*   컨텍스트 윈도우
    
    *   LLM이 한 번에 처리할 수 있는 최대 토큰 수. 시스템 프롬프트+문서+질문+답변의 합이 한도를 넘으면 안 된다.
        

*   핵심 비유
    
    *   Gen AI = 자동차. 엔진=모델(LLM), 완성차=RAG·에이전트, 튜닝=LLM 최적화, 운전=서빙
        

**검색 품질 끌어올리기**

적용 단계별로 보면 다음과 같슴다.

*   검색 전(Pre-retrieval) : Query Expansion, HyDE
    
*   검색 중(Retrieval) : Hybrid Search
    
*   검색 후(Post-retrieval) : Reranking
    
*   대화형 : Conversational RAG
    

*   Hybrid Search
    
    *   Dense(의미) + Sparse(키워드, TF-IDF/BM25) 검색을 가중합으로 결합한다.
        
    *   final\_score = alpha _dense + (1 - alpha)_ sparse
        
    *   Dense만 쓰면 키워드를 놓치고, Sparse만 쓰면 동의어를 놓치기 때문에 쓴다.
        

*   Query Expansion
    
    *   질문이 짧거나 모호할 때 검색 범위를 넓히는 기법이다.
        
        *   유의어 추가 / Multi-Query(수평 확장) / Step-back(수직 확장)
            

*   Reranking
    
    *   1차(Bi-Encoder, 빠름·낮은 정확도)로 후보를 빠르게 뽑고, 2차(Cross-Encoder, 느림/높은 정확도)로 재평가해 정밀도를 높인다.
        

*   HyDE (Hypothetical Document Embeddings)
    
    *   질문 -> 가상 답변 생성 -> 가상 답변을 임베딩 -> 실제 문서 검색. 가상 답변이 사실과 달라도 의미 방향만 맞으면 검색이 잘 된다.
        

*   Conversational RAG (★ 실무에서 가장 중요)
    
    *   이전 대화를 참고해 "그것", "가격은?" 같은 맥락 의존 질문을 독립형 질문으로 재구성한 뒤 검색/생성한다.
        

**잘 만들었는지 측정하기**

*   RAG Evaluation
    
    *   검색/생성 품질을 "느낌"이 아니라 숫자로 진단한다. 검색과 생성을 나눠서 평가하는 게 핵심이다.
        
        *   검색 : Context Precision(노이즈가 적은가) / Context Recall(빠뜨리지 않았는가)
            
        *   생성 : Faithfulness(환각 체크) / Answer Relevancy(질문 의도에 맞는가)
            

*   평가 데이터셋 4요소
    
    *   question / ground\_truth / contexts / answer
        

*   결과 해석
    
    *   검색 실패 : Precision 낮음 + Recall 낮음 -> 임베딩/청킹 개선, Hybrid Search
        
    *   검색 노이즈 : Recall 높음 + Precision 낮음 -> Reranking 도입
        
    *   생성 실패 : Faithfulness 낮음 -> 프롬프트/모델 개선
        
    *   답변 이탈 : Answer Relevancy 낮음 -> 질문 의도 재확인 지시
        

*   LLM-as-a-Judge
    
    *   규칙 기반은 의미가 같아도 표현이 다르면 0점 처리되는 한계가 있어서, LLM이 의미 수준에서 채점하게 한다.
        
        *   명확한 기준 + 단순한 출력(0~1) + 역할 부여로 채점 프롬프트를 설계한다.
            
        *   규칙 기반(빠름, 1차 점검)과 LLM-as-Judge(정밀, 의미 평가)는 대체 관계가 아니라 역할 분담이다.
