오늘 배운 내용 : 특강 및 LangGraph 고급

'자기 자신 같은 사람과 프로젝트하고 싶나' 라는 말씀이 인상 깊었습니다.

배운 토픽 (오늘은 코드 위주 아님)

**Persistence(영속성)**

*   LangGraph 그래프의 state를 실행 이후에도 유지하고, 같은 실행 흐름에서 다시 이어 사용할 수 있게 하는 **상태 유지 기능**
    
*   사용 이유 : 그래프 실행 상태를 저장하고 이어 갈 수 있게 해, 대화 연속성-장애 복구-중단 후 재개-디버깅을 안정적으로 지원하기 위해서
    
*   사용 방법 : compile(checkpointer=...)로 체크포인터를 연결하고 호출 시 thread\_id로 세션을 식별
    
*   기본 형식
    
*   그래프 컴파일 시 체크포인터 연결
    
    *   graph = builder.comile(checkpointer=<체크포인터>)
        
    *   그래프 실행 중 만들어지는 State를 유지할 수 있도록 설정하는 단계
        

*   호출 시 thread\_id 전달
    
    *   graph.invoke(<입력>, config={"configurable": {"thread\_id": " <세션 식별자>"}})
        
    *   챗봇이나 장기 워크플로에서는 thread\_id를 어떤 기준으로 만들지 미리 정해 두는 것이 중요
        

**Checkpointer**

*   LangGraph 그래프의 State를 실행 흐름별로 저장하고 다시 불러워, Persistence를 실제로 동작시키는 저장 인터페이스, 즉 **체크포인터는 영속성을 실행하는 저장 인터페이스다**
    
*   Checkpointer가 기반이 되는 기능
    
    *   대화 메모리 , 장애 복구, Human-in-the-Loop, Time Travel, 상태 조회와 수정
        
*   사용 이유 : 그래프 State 저장과 복원을 표준화해 실행 흐름의 연속성, 장애 복구, 중복 실행 방지, 운영 디버깅을 안정적으로 지원하기 위해서
    
*   사용 방법 : 환경에 맞는 Checkpointer 구현체를 골라 인스턴스를 만들고 builder.comile(checkpointer=...)로 그래프에 연결
    
    *   동작 4단계
        
        *   1단계 : Checkpointer 선택
            
            *   실행 환경에 맞는 Checkpointer 구현체를 선택
                
        *   2단계 : 인스턴스 생성
            
            *   해당 Checkpointer 구현체를 임포트해 인스턴스를 생성
                
        *   3단계 : 그래프에 연결
            
            *   그래프 빌더에 노드와 엣지를 등록한 뒤 builder.compile(checkpointer=...)로 컴파일해 그래프에 Checkpointer를 연결
                
        *   4단계 : thread\_id 지정 실행
            
            *   호출 시 config={"configurable": { thread\_id":"..."}}를 함께 전달. 같은 thread.id로 다시 호출하면 이전 state가 자동으로 이어짐
                

**thread**

*   같은 thread\_id로 묶인 여러 번의 그래프 실행이 하나의 흐름으로 이어지는 LangGraph의 실행 세션 단위 (LangGraph에서 그래프는 invoke()를 호출할 때마다 실행됨)
    
*   사용 이유 : 사용자-대화-작업별 실행 흐름을 분리해 상태 혼선을 막고, 같은 흐름 안에서는 이전 State를 안정적으로 이어 가기 위해서
    
*   사용 방법 : invoke() 호출 시 config={"configurable": {"thread\_id": "고유값"}}을 전달하여 세션을 식별
    
    *   동작 5단계
        
        *   1단계 : 체크포인터 연결
            
            *   builder.comile(checkpointer=...)로 그래프에 체크포인터를 연결함. 체크포인터가 없으면 Thread가 의미를 가지지 않음
                
        *   2단계 : thread\_id 설계
            
            *   사용자 ID, 세션 ID, 작업 ID등 세션을 구분할 수 있는 고유 문자열을 정함
                
        *   3단계 : config 구성
            
            *   config={"configurable": {"thread\_id": "고유값"}} 형태로 만듬
                
        *   4단계 : invoke() 호출
            
            *   graph.invoke(input, config)로 호출. 같은 thread\_id로 다시 호출하면 이전 상태가 자동으로 이어짐
                
        *   5단계 : 상태 조회-수정
            
            *   필요 시 graph.get\_state(config)로 현재 상태를, graph.get\_state\_history(config)로 체크포인트 이력을 확인, graph.update\_state(config, values)로 상태를 직접 수정
                

**checkpoint**

*   한 Thread 안에서 그래프 실행 중 특정 시점마다 저장되는 State 스냅샷
    
*   사용 이유 : 그래프 실행 과정을 시점별로 복원 가능하게 남겨, 실패 복구-흐름 재개-문제 추적-분기 실험을 안정적으로 수행하기 위해
    
*   사용 방법 : Checkpointer를 연결한 그래프를 호출하면 노드 실행마다 자동 생성되며, get\_state()와 get\_state\_history()로 조회하고 update\_state()로 수정
    
    *   동작 6단계
        
        *   1단계 : Checkpointer 연결
            
            *   builder.compile(checkpointer=...)로 그래프에 Checkpointer를 붙임
                
        *   2단계 : Thread 식별자 부여
            
            *   config={"configurable": {"thread\_id":"고유값"}}을 전달함
                
        *   3단계 : 그래프 실행
            
            *   graph.invoke(input, config)를 호출
                
        *   4단계 : 최신 Checkpoint 조회
            
            *   graph.get\_state(config)로 마지막 Checkpoint의 State와 다음 실행 노드를 확인
                
        *   5단계 : Checkpoint 이력 조회
            
            *   graph.get\_state(config)로 누적된 Checkpoint를 시간 역순으로 순회함
                
        *   6단계 : 상태 수정 후 재개
            
            *   graph.update\_state(config, values)로 현재 Checkpoint를 갱신한 뒤 graph.invoke(None, config)로 그 지점에서 이어서 실행함
                

**Time Travel**

*   과거 Checkpoint를 기준으로 그래프 실행을 다시 이어 가거나, 다른 입력으로 재실행해 새로운 분기를 만드는 LangGraph 기능
    
*   사용 이유 : 과거 시점의 실행을 그대로 재현하거나, 그 시점에서 다른 선택을 시도해 보면서 디버깅과 대안 탐색을 하기 위해서
    
*   사용 방법 : graph.get\_state\_history(config)로 과거 Checkpoint를 조회한 뒤, checkpoint\_id를 포함한 config로 graph.invoke(...)를 호출
    
    *   동작 6단계
        
        *   1단계 : checkpointer 연결한 그래프 준비
            
            *   builder.compile(checkpointer=...)로 Checkpointer를 연결합니다.
                
        *   2단계 : 정상 실행으로 Checkpoint 누적
            
            *   thread\_id를 정한 config로 그래프를 여러 번 실행합니다.
                
        *   3단계 : 이력 조회
            
            *   graph.get\_state\_history(config)로 Thread의 모든 Checkpoint를 시간 역순으로 순회하면서, 돌아가고 싶은 시점을 고름
                
        *   4단계 : target\_config 구성
            
            *   config에 thread\_id와 함께 선택한 Checkpoint의 checkpoint\_id를 넣어 target\_config를 만듬
                
        *   5단계 : 과거 시점에서 새 입력으로 재실행
            
            *   graph.invoke(새\_입력, target\_config)로 호출하면, 그 시점의 State 위에 새 입력이 더해져 새로운 분기가 생깁
                
        *   6단계 : 결과 비교
            
            *   기존 실행 경로와 새 분기의 Checkpoint를 함께 비교하며 디버깅하거나, 둘 중 더 좋은 결과를 선택함
                

**Durable Execution**

*   그래프 실행이 중간에 끊겨도 Checkpoint에 저장된 State를 기준으로, 같은 흐름을 안전하게 이어 실행할 수 있게 하는 LangGraph의 실행 모델
    
*   사용 이유 : LLM·외부 API 호출이 길게 이어지는 장기 실행 워크플로가 도중에 끊겨도 처음부터 다시 시작하지 않고 마지막 Checkpoint에서 이어 실행하기 위해서
    
*   사용 방법 : Checkpointer를 연결하고, 비결정적·부수 효과 작업을 @task 또는 노드로 격리한 뒤, 같은 thread\_id로 다시 호출해 마지막 Checkpoint에서 재개
    
    *   동작 7단계
        
        *   1단계 : Checkpointer
            
            *   builder.compile(checkpointer=...)로 그래프에 Checkpointer를 연결합니다.
                
        *   2단계 : thread\_id 설계
            
            *   같은 실행 흐름으로 이어야 하는 호출에 같은 thread\_id를 사용함
                
        *   3단계 : 그래프 실행
            
            *   graph.invoke(input, config) 형태로 그래프를 실행함
                
        *   4단계 : Checkpoint 누적
            
            *   그래프가 실행되면서 각 실행 단계의 State가 Checkpoint로 저장됨
                
        *   5단계 : 장애 또는 중단 발생
            
            *   실행 중 서버 재시작, 네트워크 오류, 외부 API 실패, 사용자 승인 대기 등으로 흐름이 끊길 수 있음
                
        *   6단계 : 같은 thread\_id로 재호출
            
            *   같은 thread\_id로 다시 호출하면 LangGraph는 마지막 Checkpoint를 기준으로 실행 흐름을 복원함
                
        *   7단계 : 상태 확인
            
            *   필요하면 graph.get\_state(config)나 graph.get\_state\_history(config)로 현재 State와 Checkpoint 이력을 확인 가능
                

**Determinism**

*   같은 입력-state-code로 다시 실행했을 때, 그래프가 같은 실행 경로와 결과를 재현할 수 있게 하는 LangGraph Durable Execution의 일관성 원칙
    
*   사용 이유 : 재실행해도 같은 흐름과 결과를 재현할 수 있게 해, 장애 복구-디버깅-테스트-운영 판단을 신뢰할 수 있게 만들기 위해
    
*   사용 방법 : LLM 호출-API 호출-랜덤-시간 조회 같은 비결정적 작업을 @task나 노드 단위로 분리해, 재실행 시 같은 흐름을 안정적으로 복원할 수 있게 설계
    
    *   동작 5단계
        
        *   1단계 : 비결정적 작업 식별
            
            *   LLM 호출, 외부 API 호출, 랜덤 값 생성, 현재 시간 조회처럼 같은 입력으로 다시 실행해도 결과가 달라질 수 있는 작업을 찾음
                
        *   2단계 : 실행 단위 분리
            
            *   Functional API에서는 @task, Graph API에서는 별도 노드로 분리
                
        *   3단계 : 워크플로 본체 단순화
            
            *   @entrypoint 본체나 라우팅 함수 안에서 비결정적 작업을 직접 호출하지 않음
                
        *   4단계 : Checkpointer 연결
            
            *   @entrypoint(checkpointer=...) 또는 compile(checkpointer=...)로 Checkpointer를 연결
                
        *   5단계 : 재실행 가능성 점검
            
            *   장애 복구나 replay 상황에서 같은 Checkpoint를 기준으로 실행 흐름이 일관되게 이어지는지 확인
                

**Idempotency(멱등성)**

멱등성 : 연산을 여러번 적용하더라도 결과가 처음과 완전히 똑같은 성질

*   같은 작업이 재실행이나 재시도로 여러 번 호출되어도 외부 시스템에 미치는 효과가 한번 실행한 것과 동일하도록 보장하는 성질
    
*   사용 이유 : 위와 같은 상황에서도 결제-이메일-DB 쓰기 같은 외부 효과가 한 번만 발생하도록 보장해, 비용 손실과 사용자 신뢰 훼손을 막기 위해
    
*   사용 방법 : 요청마다 고유한 idempotency key를 부여하고, 외부 호출 직전 처리 이력을 확인한 뒤 처리 완료 시 그 기록을 남기는 방식으로 직접 구현
    
    *   구현 5단계
        
        *   1단계 : 키 설계
            
            *   같은 작업을 식벼할 수 있는 안정적인 문자열을 정함
                
        *   2단계 : 처리 이력 저장소 준비
            
            *   키와 처리 결과를 보관할 저장소(DB 테이블, Redis 등)를 둔다
                
        *   3단계 : 외부 호출 직전 조회
            
            *   키로 이력을 조회해 이미 처리된 작업인지 확인
                
        *   4단계 : 실제 호출 후 기록
            
            *   외부 호출이 성공하면 그 키와 결과를 저장
                
        *   5단계 : 서버 측 키 활용
            
            *   외부 API가 Idempotency-Key 헤더 같은 기능을 제공한다면 함께 사용함
