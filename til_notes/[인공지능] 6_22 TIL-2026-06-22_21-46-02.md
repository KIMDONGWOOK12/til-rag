배운 내용 : LangChain (LCEL, Runnable, 프롬프트/출력, 대화 관리, Document Loader)

TIL 정리 할 내용이 많아서 고유명사, 사용이유, 동작 방식과 코드로 정리해두겠슴다

**LangChain**

*   LLM 애플리케이션 개발에 반복적으로 필요한 기능(프롬프트, 모델 호출, 출력 파싱, 검색, 대화 기록)을 표준화된 컴포넌트로 제공하는 오픈소스 프레임워크
    
*   사용 이유 : 직접 하드코딩하면 모델 교체, 프롬프트 관리, 단계 추가마다 코드를 새로 짜야 하는데, 표준 부품으로 조립하면 개발이 빠르고 교체/확장이 쉽기 때문
    
*   동작 방식 : 각 단계(프롬프트 작성 -> 모델 호출 -> 출력 파싱 -> 검색)를 독립 컴포넌트로 분리하고 파이프(|)로 연결
    

    직접 짠 rag() 함수가 LangChain에선 한 줄
    retriever | prompt | model | parser

**LCEL (LangChain Expression Language)**

*   파이프(|) 연산자로 Runnable 컴포넌트를 선언적으로 연결하여 체인을 구성하는 LangChain의 핵심 문법 체계
    
*   사용 이유 : 여러 단계를 일관된 방식으로 연결해 구조를 단순하게 유지하고, 중간 단계 추가/교체를 파이프 한 줄로 처리하기 위해
    
*   동작 방식 : 왼쪽 컴포넌트의 출력이 오른쪽 컴포넌트의 입력으로 자동 전달
    

    chain = prompt | model | parser
    result = chain.invoke({"question": "어댑터즈란?"})
    
    하드코딩이면 세 줄:
    prompt_result = prompt.invoke(...)
    model_result = model.invoke(prompt_result)
    parser_result = parser.invoke(model_result)

**Runnable Interface**

*   프롬프트, 모델, 파서, 커스텀 함수처럼 서로 다른 객체를 같은 방식으로 실행하기 위한 표준 메서드 규칙이다.
    
*   사용 이유 : 컴포넌트 종류가 달라도 호출 방법이 같아야 파이프(|)로 자유롭게 연결하고 확장할 수 있기 때문
    
*   동작 방식 : invoke/batch/stream 같은 공통 메서드를 모두가 구현하므로 같은 방식으로 호출됨
    

    invoke(input)  : 입력 1개 -> 출력 1개 (기본)
    batch(inputs)  : 입력 리스트 -> 출력 리스트 (병렬)
    stream(input)  : 결과를 청크 단위로 순차 반환
    ainvoke(input) : invoke의 비동기 버전
    
    일반 Python 함수는 Runnable이 아님
    -> RunnableLambda(함수)로 감싸야 체인에 연결 가능

**Messages**

*   Chat Model의 입력과 출력을 구성하는 역할별 메시지 객체의 집합이다.
    
*   사용 이유 : 시스템 규칙/사용자 질문/이전 답변을 역할로 구분해야 모델이 맥락을 정확히 이해하기 때문 (문자열 하나로 섞으면 구분 불가)
    

메시지 타입

    SystemMessage : 모델의 행동 규칙, 페르소나 지정
    HumanMessage  : 사용자 질문/요청
    AIMessage     : 모델의 이전 응답 (히스토리 구성용)
    ToolMessage   : 도구 실행 결과 전달 (에이전트용)

공통 속성 : content(본문), type(역할 문자열)

    멀티턴은 리스트에 .append()만 하면 됨
    최근 N턴 유지는 messages[-2*N:] 슬라이싱
    역할 필터링은 [m for m in messages if m.type == "human"]

**PromptTemplate**

*   변수 자리표시자({variable})를 포함한 프롬프트 문자열을 객체로 관리하고, 실행 시점에 값을 주입해 완성된 프롬프트를 생성하는 클래스
    
*   사용 이유 : 프롬프트를 매번 f-string으로 새로 짜지 않고, 틀은 고정하고 값만 바꿔 재사용/일관성 관리하기 위해
    
*   동작 방식 : from\_template로 틀을 만들고 invoke로 값 주입
    

    prompt = PromptTemplate.from_template("{topic}에 대해 {length}자로 설명하세요.")
    result = prompt.invoke({"topic": "어댑터즈", "length": "100"})
    
    단일 문자열 프롬프트 생성 (역할 구분 없음)

**ChatPromptTemplate**

*   역할별(System/Human/AI) 메시지 리스트를 구성하는 프롬프트 템플릿 클래스다.
    
*   사용 이유 : PromptTemplate과 달리 시스템 지시와 사용자 입력을 역할별로 분리한 채 템플릿화할 수 있어, 대화형 프롬프트를 정확하게 관리하기 위해
    
*   동작 방식 : from\_messages에 (역할, 내용) 튜플 리스트를 전달
    

    prompt = ChatPromptTemplate.from_messages([
        ("system", "당신은 {role} 전문가입니다."),
        ("human", "{question}")
    ])
    
    튜플 키워드 매핑
    "system"          -> SystemMessage
    "human"/"user"    -> HumanMessage
    "ai"/"assistant"  -> AIMessage
    
    Chat Model 사용 시 표준 (실무에서 가장 많이 씀)

**FewShotPromptTemplate**

*   소수(2~5개)의 입출력 예시를 프롬프트에 자동 삽입해, LLM이 원하는 형식과 패턴으로 응답하도록 유도하는 템플릿 클래스다.
    
*   사용 이유 : "이렇게 해라"를 설명하는 것보다 "이런 식으로 해라"를 예시로 보여주면 출력 형식/길이/판단 기준이 더 안정적이기 때문
    

Zero-Shot vs Few-Shot

    Zero-Shot : 예시 없이 지시만 (단순 작업에 빠름)
    Few-Shot  : 예시 2~5개 보여주고 같은 패턴으로 답하게 함

구성 요소

    examples       : 입출력 예시 리스트 (각 딕셔너리 1개가 1 shot)
    example_prompt : 각 예시를 표현할 형식 (PromptTemplate)
    prefix         : 예시 앞 텍스트 (작업 설명)
    suffix         : 예시 뒤 텍스트 (실제 입력 자리표시자)
    
    예시는 많을수록 좋은 게 아님 -> 2~5개, 품질이 핵심

**MessagesPlaceholder**

*   ChatPromptTemplate 안에서 실행 시점에 메시지 리스트가 삽입될 위치를 지정하는 컴포넌트다.
    
*   사용 이유 : 대화 기록처럼 매 요청마다 달라지는 메시지 흐름을 역할 구조 그대로 주입하면서, 프롬프트 템플릿 자체는 일관되게 유지하기 위해
    
*   동작 방식 : 템플릿에 자리를 잡아두고, invoke 시 해당 변수에 메시지 객체 리스트를 전달
    

    prompt = ChatPromptTemplate.from_messages([
        ("system", "..."),
        MessagesPlaceholder(variable_name="history"),
        ("human", "{question}")
    ])
    
    {variable}        : 단일 문자열 (메시지 1개)
    MessagesPlaceholder : 메시지 객체 리스트 (여러 개, 역할 유지)
    
    첫 질문은 history=[] 빈 리스트
    이후엔 [HumanMessage, AIMessage, ...] 누적해서 전달

**Structured Output**

*   LLM 응답을 사전에 정의한 스키마(필드명, 타입, 설명)에 맞춰 구조화된 객체로 반환하는 방식이다.
    
*   사용 이유 : 응답을 사람이 읽는 문장이 아니라 시스템이 바로 처리할 수 있는 데이터로 받아, 파싱 코드를 줄이고 후속 처리 오류를 막기 위해
    

\= 동작 방식 : Pydantic 모델로 스키마를 정의하고 with\_structured\_output으로 모델에 바인딩

    class DocumentAnalysis(BaseModel):
        title: str = Field(description="문서의 제목")
        keywords: list[str] = Field(description="핵심 키워드 3~5개")
    
    structured_model = model.with_structured_output(DocumentAnalysis)
    result = structured_model.invoke("...")
    -> result.title, result.keywords 로 바로 접근
    
    모델 레벨에서 구조를 강하게 유도 (Gemini, OpenAI 등 지원 모델)

**JsonOutputParser**

*   LLM의 텍스트 응답을 JSON(Python 딕셔너리) 형태로 파싱하는 출력 파서 클래스다.
    
*   사용 이유 : with\_structured\_output을 지원하지 않는 모델에서도 구조화된 결과를 받을 수 있고, 형식 지시를 프롬프트에 자동 주입할 수 있기 때문
    
*   동작 방식 : 프롬프트에 형식 지시를 넣고, 체인 마지막에 파서로 연결
    

    parser = JsonOutputParser(pydantic_object=DocumentAnalysis)
    chain = prompt | model | parser
    result = chain.invoke({
        "input": "...",
        "format_instructions": parser.get_format_instructions()
    })
    -> result["title"] 처럼 키로 접근 (딕셔너리)
    
    get_format_instructions() : "이 JSON 형식으로 답하라" 지시문 자동 생성

**PydanticOutputParser**

*   LLM의 텍스트 응답을 Pydantic 모델 인스턴스로 파싱하여, 타입 검증과 필드 접근을 제공하는 출력 파서 클래스다.
    
*   사용 이유 : JsonOutputParser와 같은 프롬프트 기반 방식이면서, 결과를 타입 검증된 객체로 받아 자동 유효성 검증과 속성 접근을 쓰기 위해
    
*   동작 방식 : JsonOutputParser와 구조 동일, 반환 타입만 다름
    

    parser = PydanticOutputParser(pydantic_object=DocumentAnalysis)
    chain = prompt | model | parser
    -> result.title 처럼 속성으로 접근 (Pydantic 객체)
    
    세 가지 비교
    with_structured_output : 모델 레벨 바인딩, Pydantic 객체
    JsonOutputParser       : 프롬프트 지시 + 파싱, 딕셔너리
    PydanticOutputParser   : 프롬프트 지시 + 파싱, Pydantic 객체
    
    타입이 안 맞으면 파싱 시점에 에러 -> 잘못된 결과를 미리 차단

**RunnablePassthrough**

*   LCEL 체인에서 입력 데이터를 변형 없이 다음 단계로 전달하거나, assign()으로 새 키를 추가하는 Runnable 유틸리티 클래스
    
*   사용 이유 : RAG처럼 원본 입력(질문)과 가공 데이터(검색 결과)를 함께 다음 단계로 넘겨야 할 때 필요하기 때문
    

동작 방식

    RunnablePassthrough()          : 입력을 그대로 통과
    RunnablePassthrough.assign()   : 기존 입력 유지 + 새 키 추가
    
    입력 {"question": "어댑터즈란?"}
    assign(length=lambda x: len(x["question"]))
    -> {"question": "어댑터즈란?", "length": 6}
    
    RAG 패턴: question은 원본 유지, context는 검색 결과 추가

**RunnableParallel**

*   여러 Runnable을 동일한 입력으로 동시에 실행하고, 각 결과를 키에 매핑해 하나의 딕셔너리로 합쳐 반환하는 Runnable 유틸리티 클래스다.
    
*   사용 이유 : 같은 입력으로 여러 처리를 동시에 해서 결과를 한 번에 모아야 할 때, 순차 실행보다 빠르고 코드가 명확하기 때문
    
*   동작 방식 : 하나의 입력이 모든 Runnable에 전달되고 결과가 딕셔너리로 합쳐짐
    

    setup = RunnableParallel(
        context=lambda x: document,      # 검색 결과 자리
        question=RunnablePassthrough()   # 원본 질문 그대로
    )
    chain = setup | prompt | model | parser
    
    딕셔너리 축약 표기도 가능 (LCEL이 자동 변환)
    setup = {"context": ..., "question": RunnablePassthrough()}

**RunnableBranch**

*   입력 조건에 따라 서로 다른 Runnable을 실행하도록 분기하는 Runnable 유틸리티 클래스다 (체인 안의 if-else).
    
*   사용 이유 : 입력 종류에 따라 다른 프롬프트/체인을 써야 할 때, 분기 로직 자체를 체인의 일부로 깔끔하게 표현하기 위해
    
*   동작 방식 : (조건, Runnable) 쌍을 순서대로 등록, 마지막에 기본 Runnable
    

    branch = RunnableBranch(
        (lambda x: "코드" in x["input"], code_chain),
        (lambda x: "어댑터즈" in x["input"], service_chain),
        default_chain   # 모든 조건 False면 실행
    )
    
    위에서부터 평가, 가장 먼저 True인 조건만 실행
    -> 구체적인 조건을 위에 둠

**RunnableWithMessageHistory**

*   기존 LCEL 체인을 감싸서, 세션 ID를 기준으로 대화 이력을 자동으로 불러오고 저장하는 Runnable 래퍼 클래스다.
    
*   사용 이유 : 사용자별 대화를 기억하는 챗봇을 만들 때, 이력 불러오기/주입/저장 반복 코드를 직접 짜지 않기 위해
    
*   동작 방식 : 세션 ID로 이력을 구분, invoke 때 config로 세션 지정
    

    config={"configurable": {"session_id": "user-001"}}
    
    처리 흐름
    1. session_id 확인
    2. 해당 세션 이력 불러오기
    3. MessagesPlaceholder 자리에 주입
    4. 체인 실행
    5. 새 대화(입력+응답)를 이력에 저장
    
    user-001, user-002는 이력이 섞이지 않음

**Message Trimming**

*   대화 이력이 LLM의 토큰 한도를 초과하지 않도록, 정해진 기준(개수/토큰 수)에 맞춰 오래된 메시지를 제거하는 처리다.
    
*   사용 이유 : 대화가 길어지면 이력이 토큰 한도를 넘어 호출 실패하거나 비용이 급증하는데, 최근 맥락만 유지하며 자동으로 막기 위해
    
*   동작 방식 : trim\_messages로 자르고, token\_counter로 기준 결정
    

    trimmed = trim_messages(
        messages,
        max_tokens=4,          # 유지할 최대값
        strategy="last",       # 최근 메시지 우선 유지
        token_counter=len,     # len=개수 / model=실제 토큰 수
        include_system=True,   # System 메시지는 항상 보존
        start_on="human",      # 결과 첫 메시지를 Human으로
    )
    
    한국어는 글자 수보다 토큰이 많음 (글자당 1.5~2 토큰) -> 주의
    초반 대화가 잘려도 System(페르소나)은 유지되므로 품질 큰 저하 없음

**Document**

*   LangChain에서 문서 한 조각을 표현하는 표준 데이터 객체다.
    
*   사용 이유 : RAG 파이프라인의 모든 단계가 같은 형식으로 문서를 주고받고, 텍스트와 출처를 함께 보관해 답변 근거를 추적하기 위해
    

두 필드

    page_content : 실제 텍스트 (임베딩/검색 대상)
    metadata     : 출처(source), 페이지(page), URL 등 부가 정보 (딕셔너리)
    
    doc = Document(
        page_content="어댑터즈는 ... 서비스입니다.",
        metadata={"source": "intro.txt", "page": 1}
    )
    
    모든 컴포넌트가 Document로 입출력 -> 단계 사이 변환 코드 불필요

**Document Loader**

*   다양한 형식의 외부 데이터를 읽어 LangChain의 Document 객체 리스트로 반환하는 컴포넌트의 표준 인터페이스다.
    
*   사용 이유 : 파일 형식이 달라도 동일한 방식(load, lazy\_load)으로 읽어 Document로 통일해, 형식별 분기 코드를 없애기 위해
    

표준 메서드

    load()      : 모든 데이터를 한 번에 리스트로 (작은 파일/실습)
    lazy_load() : Document를 하나씩 반환 (큰 파일/운영, 메모리 절약)

**TextLoader**

*   .txt, .md 같은 단일 텍스트 파일을 읽어 한 개의 Document로 변환하는 Document Loader 구현체다.
    
*   동작 방식 : 한 파일 = 한 Document, source에 파일 경로 자동 저장
    

    loader = TextLoader("intro.txt", encoding="utf-8")
    docs = loader.load()   # 길이 1 리스트
    
    한국어 파일은 encoding="utf-8" 거의 필수 (안 하면 깨짐)

**PyPDFLoader**

*   pypdf 라이브러리로 PDF를 읽고, 페이지마다 한 개의 Document로 변환하는 Document Loader 구현체다.
    
*   사용 이유 : PDF 기반 RAG에서 페이지별 근거 추적("이 답변은 3페이지에서")을 유지하기 위해
    
*   동작 방식 : 페이지마다 1 Document, metadata에 source와 page 자동 저장
    

    loader = PyPDFLoader("sample.pdf")
    docs = loader.load()   # 10페이지면 Document 10개
    
    metadata["page"]는 0부터 시작 -> 표시할 땐 +1

**WebBaseLoader**

*   URL을 받아 HTML을 가져온 뒤 BeautifulSoup으로 파싱하여 본문 텍스트를 Document로 변환하는 Document Loader 구현체다.
    

    BeautifulSoup : HTML/XML을 파싱해 원하는 태그/텍스트/속성을 추출하는 Python 라이브러리

사용 이유 : 회사 블로그, 공식 문서, FAQ 같은 웹 자료를 원문 출처(URL) 추적과 함께 RAG에 넣기 위해

동작 방식 : URL 1개 = Document 1개, source/title/description/language 자동 저장

    loader = WebBaseLoader("https://example.com/article")
    docs = loader.load()
    
    bs_kwargs로 본문 영역만 파싱 (메뉴/사이드바/푸터 제외)
    bs_kwargs={"parse_only": bs4.SoupStrainer(class_="article-body")}
    
    정적 HTML에 적합
    JS로 본문이 생성되는 동적 페이지는 SeleniumURLLoader / PlaywrightURLLoader

**DirectoryLoader**

*   지정된 디렉터리 안의 여러 파일을 glob 패턴으로 골라 내부 로더로 일괄 처리하여 Document 리스트로 변환하는 Document Loader 구현체
    

    glob 패턴 : *.txt, **/*.md 처럼 와일드카드로 조건에 맞는 파일을 찾는 규칙

*   사용 이유 : 여러 파일로 흩어진 문서를 하나의 RAG 데이터셋으로 통합하면서, 어느 파일에서 나왔는지 추적을 유지하기 위해
    
*   동작 방식 : 파일을 찾아 loader\_cls로 지정한 로더에 넘김 (직접 읽지 않음)
    

    loader = DirectoryLoader(
        path="docs",
        glob="**/*.txt",                     # 하위 폴더까지 .txt
        loader_cls=TextLoader,               # 실제 읽기는 TextLoader
        loader_kwargs={"encoding": "utf-8"}
    )
    docs = loader.load()
    
    glob 패턴
    *.txt    : 현재 폴더 바로 아래 .txt만
    **/*.txt : 하위 폴더까지 모든 .txt
    
    한 번에 한 가지 loader_cls만 받음
    -> 형식이 섞이면 형식별로 따로 만들고 결과를 합침 (md_docs + pdf_docs)
